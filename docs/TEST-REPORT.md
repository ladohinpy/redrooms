# Проверки сборки admin-releases-v1

Дата: 19 октября 2026. Node.js 22.16.0, встроенная SQLite Node, Chromium/Playwright.

## Выполнено

**100 автоматических Node-проверок — 100 пройдено, 0 ошибок, 0 пропусков.**
Проверены роли и подделка клиентского userId, положительный/отрицательный результат подписки,
ошибки сети, приоритет параметров, отсутствие fallback, все основные переходы каталога/релиза,
неизменяемость опубликованного каталога, архивирование и защита default, ограничение истории,
CSV/JSON и недопустимые данные, UTF-8, дубликаты и ограничения размеров.

Проверены сохранение исходника сборщиком, отказ до изменения файлов при отсутствии ID или
несовпадении маркеров, повторяемость build hashes, сохранение старых зависимостей, сосуществование
двух идентифицированных сборок, запрет подмены старой версии под прежним ID.

Реальный файл `tgcloud/lib/rr/store.js` выполнен с локальным адаптером формы SDK поверх настоящей
SQLite: вставка/чтение JSON, повторная инициализация без сброса, условное изменение revision
и отказ устаревшему сохранению. Это проверка SQL-семантики, **не проверка облачной реализации SDK**.

**12 браузерных DOM-сценариев — 12 пройдено.** Реальные модули интерфейса проверены в Chromium
с синтетическим Telegram SDK и локальным Node-сервисом: доступ администратора, копирование
каталога, выбор/загрузка CSV-файла, модерация, сохранение, публикация каталога, создание релиза,
публикация и переключение default, отказ постороннему аккаунту, мобильная ширина 390 px без
горизонтального переполнения, безопасный текст вместо HTML, сохранность несохранённого текста
после конфликта. В этом сценарии нет необработанных браузерных JS-ошибок.

Снимки в `docs/previews/` сделаны с тестовыми данными и синтетическими ID 101/202.
Это не фотографии/ID пользователей и не снимки production.

## Ограничения — что НЕ проверено

- Полный актуальный исходный HTML v06 не удалось получить как raw-файл. Интеграция сборщика
  проверена на минимальном контрактном fixture, не на всей настоящей сцене с 201 кассетой.
- Не выполнен реальный вызов Telegram Serverless/миграция/production-деплой: ключ не предоставлялся,
  в рабочем приложении ничего не изменялось. `rrHealth` включён в процедуру публикации как отдельная
  проверка настоящей платформы до включения нового frontend.
- Навигация Chromium на localhost была заблокирована политикой среды. Поэтому DOM-сценарий
  выполнен офлайн с модулями как data URL и loopback-вызовами тестового Node через Python.
  Браузерные переходы, полноценный deep link, сохранение реального Telegram initData при переходах
  и работа в Telegram WebView не заявлены проверенными. Серверный выбор релиза проверен unit-тестами.
- Не тестировались настоящие Android/iOS-устройства, производительность WebGL, жесты v06,
  сохранение после закрытия настоящего Mini App и работа SDK при истёкшем initData.
- Это не аудит безопасности и не нагрузочный тест. Большие предельные наборы нужно проверять
  предпросмотром на реальных телефонах до назначения основного релиза.

## Как повторить

Только локальные автоматические тесты (сеть и ключи не нужны):

```bash
node scripts/rr-check.cjs --tests-only
```

В настоящем checkout после наложения пакета — сборка и проверка целостности:

```bash
node scripts/rr-prepare.cjs
node scripts/rr-check.cjs
```

Необязательный браузерный стенд, **только localhost и только тесты**:

```bash
node tests/rr/browser-server.mjs
# В другом терминале, при установленном Python Playwright и Chromium:
python tests/rr/browser-smoke.py
```

Полный навигационный `browser-smoke.py` включён для запуска в среде без указанного ограничения;
в этой сессии он остановился на заблокированной навигации. Выполненный вариант:

```bash
python tests/rr/browser-offline.py
```

Укажите `CHROMIUM` и `RR_TEST_OUTPUT` под вашу систему при необходимости. Перед повторным
браузерным прогоном перезапустите локальный Node-стенд, чтобы получить чистую тестовую БД.
Никогда не переносите этот стенд в `public`, не публикуйте его как серверный handler и
не используйте синтетический SDK вместо Telegram в production.

Дополнительно выполнены полная последовательность prepare → check после сборки и проверка ZIP-упаковщика на отдельном fixture-checkout. Целостность ZIP проверена; секретные/локальные конфиги в него не попали. Это не подменяет сборку полного main.
