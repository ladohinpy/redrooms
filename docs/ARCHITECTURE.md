# Архитектура admin-releases-v1

## Граница исходников

Пакет не содержит полного снимка исходной v06 из `main`: raw-скачивание репозитория и
материализация предыдущего ZIP были недоступны. Он не является заменой всей папки проекта.
Текущий HTML берётся из checkout получателя. Сборщик сохраняет его как `src/rr-legacy-v06.html`.
Адаптер привязан к прочитанному контракту v06 и останавливается при несовпадении маркеров.
Таким образом исходная игра не восстанавливается по памяти и не подменяется тестовой сценой.

## Поток запуска

1. Корневой `public/index.html` поднимает официальный Telegram SDK и вызывает `rrGetLaunch`.
2. Платформа проверяет initData; сервис использует только `ctx.initData.user.id`.
3. Проверяется подписка существующим `checkAccess`, затем разрешается селектор релиза.
4. Клиент переходит на разрешённый same-origin путь `/games/<id>/<hash>/index.html`, сохраняя
   Telegram query/hash и явно фиксируя `release`.
5. Встроенный адаптер перед `launchArchive` повторно получает разрешённый релиз и каталог,
   задаёт JSON в `default-dataset` и namespace сохранений. Затем продолжает исходную игру.
6. Уже работающая игра не получает push/опросов о новом default.

Повторные проверки при переходе намеренны: прямой вход на игровой HTML не должен превращать
интерфейс в обход контроля. Исходный gate также сохранён, поэтому при запуске возможны несколько
обращений к проверке подписки. Это не периодический мониторинг членства и не античит.

Сервер выбирает сборку только из реестра, подготовленного разработчиком. `release`, `game`
и `startapp` — только идентификаторы. Они не интерпретируются как имя произвольного файла,
внешний URL, код, SQL или ветка GitHub.

## Логические сущности и физическое хранение

```text
rr_admin_state
  id        TEXT PRIMARY KEY   // "application"
  revision  INTEGER NOT NULL   // общий optimistic-lock номер
  state_json TEXT NOT NULL     // json() в sdk/db

state_json:
  schemaVersion: 1
  game_versions: []
  catalog_versions: []
  game_releases: []
  app_settings: { defaultReleaseId, gameDefaults: [] }
  audit: []
```

В `game_versions` — ID, имя, entry, SHA-256, версия схемы каталога, aliases.
В `catalog_versions` — ID редакторской версии, name, status, revision, нормализованный
редакторский catalog, зафиксированный playable после публикации и сведения об изменении.
В `game_releases` — ID, gameVersionId, catalogVersionId, codeHash, draft/published/archived,
public/unlisted и даты. Содержимое опубликованного каталога не меняется.

Все административные команды — чистое преобразование документа и один условный UPDATE:

```sql
UPDATE rr_admin_state
SET revision = :next_revision, state_json = :new_state
WHERE id = :id AND revision = :expected_revision
RETURNING *;
```

Если возвращена пустая выборка, произошёл конфликт. Если команда невалидна, UPDATE не выполняется.
Переключение default, связанных указателей и история входят в один JSON и в одну запись SQLite.
Повторная инициализация использует upsert, который меняет только ключ на самого себя — не seed,
не revision и не пользовательские данные. Новая схема добавляется к существующей, не заменяет её.

Это простой двухадминистраторский MVP, не универсальное хранилище большой кинобазы.
Лимиты и необходимость будущего построчного разбиения описаны в README. Никакой автоматической
очистки старых каталогов или опубликованных игровых файлов при деплое нет.

## API

Все вызовы — `Telegram.WebApp.Serverless.call(name, input, callback)`.

| Endpoint | Доступ | Вход | Выход |
|---|---|---|---|
| `rrAdminStatus` | Любой проверенный Telegram user | `{}` | Собственный userId, isAdmin, configured; botUsername только админу при доступном getMe |
| `rrAdminRead` | Администратор | `{}` | revision, state, availableGames, limits |
| `rrAdminCommand` | Администратор | expectedRevision, action, input | Актуальная revision и состояние |
| `rrGetLaunch` | Проверенный подписчик; admin route без подписки | release / game / default | Разрешённый релиз, сборка, каталог, userId, isAdmin |
| `rrHealth` | Администратор | `{}` | Краткий smoke-ответ, revision, defaultReleaseId, количество каталогов/сборок |

`rrGetLaunch` берёт start_param из проверенного контекста платформы, не из входного `input`.
Ключ `default: true` игнорирует start_param, но не предоставляет прав и не отменяет подписку.
Он используется кнопкой перехода к текущей основной игре.

Команды: `createCatalog`, `cloneCatalog`, `saveCatalog`, `publishCatalog`, `syncGames`,
`createRelease`, `publishRelease`, `setDefault`, `setGameDefault`, `archiveRelease`, `restoreRelease`.
Пример:

```json
{
  "expectedRevision": 8,
  "action": "setDefault",
  "input": {"id": "classic-2"}
}
```

В `EndpointError.parameters.code` возвращаются, в частности, `AUTH_REQUIRED`, `FORBIDDEN`,
`CONFLICT`, `VALIDATION`, `DUPLICATE`, `PENDING_REVIEW`, `IMMUTABLE`, `NOT_FOUND`,
`NOT_PUBLISHED`, `BUILD_UNAVAILABLE`, `INCOMPATIBLE`, `DEFAULT_IN_USE`, `CAPACITY`.
Ошибка подписки может содержать проверенный `joinUrl`. Внутренние ошибки не преобразуются
в успешный ответ. При таймауте клиент не может знать, успела ли серверная запись завершиться.

## Неизменяемые сборки

`config/rr-built-games.json` хранит sourceHash, codeHash, entry и hashes зафиксированных
runtime/script-файлов. SHA-256 используется для целостности сборки; это не авторизация игрока.
Повторная сборка старого ID проверяет исходный hash и наличие старых файлов, а не переписывает их.
Локальные внешние script-зависимости, например исходный access-gate, копируются в `public/rr/frozen`.
Удалённый Telegram SDK остаётся внешней зависимостью, не замораживается и не перепубликуется.

Текущий адаптер рассчитан на самодостаточную v06. Более сложные новые игры с относительными
импортами внутри внешних script-файлов, отдельными CSS/ресурсами или другой схемой каталога
требуют собственного сборщика/адаптера. Не выдавайте текущую схему за универсальную систему сборки.

## Защитные границы

Права обоих администраторов равны. Второе независимое одобрение не требуется: тот же человек
может сохранить и опубликовать. Для разделения обязанностей нужен следующий слой ролей.
Импорт файла — только локальная обработка, затем явный server-side save с повторной валидацией.
Статические файлы общедоступны; ссылки на черновик не являются секретом, доступ решает сервер.
Непубликованный код не является конфиденциальным только потому, что релиз имеет status=draft.

Нет автоматической привязки новой Git-ветки к новой среде. Один CLI token означает одно
приложение/одну БД. Разные ветки, опубликованные этим ключом, меняют тот же сервер.
