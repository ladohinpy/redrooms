# Установка конкурсного пакета 1

## Что это за архив
Полный обновлённый проект поверх присланного main `99897cfa7a69b42b944e0ef14caedac983d95052`.
Есть миграция и новая сборка v09. Исходные опубликованные v06/v07/v08 сохранены.
На ваш сервер из чата ничего не публиковалось, сообщения ботом не отправлялись.

## Перед первым запуском

1. Павел и Виталий **каждый из своего Telegram** открывают личный чат с
   `@vitalkino_stage_bot` и нажимают «Начать», если ещё не делали этого. Не блокируйте
   бота: он должен прислать JSON-копию каждому. Это требование только к администраторам.
2. GitHub → Settings → Secrets and variables → Actions → **Variables**:
   - `RR_ADMIN_IDS`: ваши прежние два числовых Telegram ID через запятую. Нужна именно
     сохранённая переменная: расписание не может взять ID из прошлой формы Run workflow.
   - `RR_STAGE_BOT_USERNAME`: `vitalkino_stage_bot`, без `@`.
3. Прежний **Secret** `TGCLOUD_TOKEN` остаётся. Это Serverless CLI Access token, не Bot API token.
4. Из нынешней админки сохраните JSON вручную. На время первого перехода закройте
   редактор и не проводите конкурс: старый backend и новая схема не должны изменяться
   одновременно вручную. Публикация ещё раз сама отправит свежую копию.

## Обновление через GitHub

1. Создать ветку `feature/contest-package-1` от текущего `main`.
2. Распаковать архив. Перенести **содержимое его папки redrooms/** в корень репозитория,
   включая `.github`. Не загружать сам ZIP как единственный файл. Не создавать второй
   уровень папок в репозитории. Остальные свои файлы не удалять.
3. Создать PR, дождаться проверок и объединить с `main`.
4. Actions → **Publish Red Room — Admin & Releases** → **новый Run workflow**,
   ветка `main`, `confirm=PUBLISH`, admin_ids можно оставить пустым при заполненной RR_ADMIN_IDS.
5. В начале Action должны успешно пройти проверка имени бота и отправка копий.
   При отказе доставки не отключать защиту: открыть чат обоим администраторам,
   проверить ID/ключ/имя и повторить новый запуск.
6. Добавочная миграция создаст `rr_records` и индексы. Ручную миграцию в BotFather
   одновременно не запускать. Старую `rr_admin_state` не удалять.
7. После зелёного результата закрыть старую Mini App и открыть:
   `https://t.me/vitalkino_stage_bot?startapp=admin`.
   Должны появиться вкладки «Материалы», «Конкурс», «Статистика», «Игроки»,
   «Публикации», «Выпуски», «Резервные копии».

Адрес Main Mini App для нынешнего бота остаётся `https://app8804859840.tgcloud.ai/`.
Ключ, база и ссылка текущего stage не меняются. PR сам по себе не публикует приложение.
`Re-run` старого задания не заменяет новый запуск с новым коммитом.

## Первая приёмка на stage

- Под обоими админскими аккаунтами сохранить небольшой набор: 4 стола × 2 кассеты.
- Добавить вступление, успешный/неуспешный финал, статью и ссылку. Проверить предпросмотры.
- Опубликовать набор по ссылке и отдельно включить конкурс. Администратор всегда
  играет вне зачёта: две попытки проверять третьим обычным подписанным аккаунтом.
- Первая попытка с одной ошибкой, вторая хуже: лучший результат не ухудшается,
  третьей конкурсной попытки нет. Проверить закрытие/повторное открытие во время игры.
- Отключить сеть на финише: не очищать localStorage; после возврата сети результат
  должен сохраниться один раз. Проверить второй телефон и разные аккаунты.
- Закрыть конкурс, проверить пометки, опубликовать итоги. Затем исключить игрока:
  прошлый итог и пост не должны поменяться; в админке появляется отдельная пометка.
- Пройти архив: рейтинг не меняется. До закрытия убедиться, что статья скрыта.
- Отправить JSON из админки и **получить два настоящих документа**. Скачать копию,
  проверить её и выполнить восстановление на stage. После восстановления создать
  новый черновик, подтвердить редактируемость и сохранность итогов.
- Обычный неподписчик видит только экран подписки. Ссылка на управление не выдаёт права.

Сначала проверяем все эти пункты; только затем переносим проверенный коммит на бой.

## Автоматические копии

Action **Red Room — Private JSON Backups** запускается ежедневно в 03:17 UTC и вручную.
После merge проверьте первый ручной запуск. Он ничего не публикует и не мигрирует —
читает согласованную базу и отправляет JSON двум администраторам.
Если бот заблокирован одним получателем, job красный; исправьте доставку, а не
скрывайте ошибку. Доставка во время подготовки архива здесь не проверялась.

## Когда понадобится production

Создайте отдельного боевого бота/Serverless-приложение. Это отдельная база и URL;
Git-ветка сама по себе отдельной среды не создаёт.

- Secret `TGCLOUD_PRODUCTION_TOKEN` — ключ именно этого бота.
- Variable `RR_PRODUCTION_BOT_USERNAME` — его точное имя, без @.
- Environment `production` — ограничить публикацию основной веткой, настроить
  подтверждение/доступ там, где это поддерживается вашим GitHub.
- Запускать **Publish Red Room — PRODUCTION**, `main`, `PUBLISH`.
- Для плановых копий боя установить variable `RR_PRODUCTION_BACKUPS_ENABLED=true`.
  Правила ручного approval environment могут остановить автоматический job на ожидании:
  настройте отдельный безопасный доступ для расписания и контролируйте его исполнения.
- Проверить, что боевой бот имеет необходимые права в проверяемом канале. Этот пакет
  не меняет существующий checkAccess: в исходниках сейчас `@redrooms_stage`, а не
  автоматически выбранный по названию канал. Переключение на настоящий канал следует
  согласовать отдельно, не отключая проверку.
- Не переносить тестовую базу поверх уже работающей боевой. Отдельные наборы переносить
  экспортом; полное восстановление чужой среды требует явного дополнительного согласия.

**Не откатывайте backend пакета 1 на прежний архив:** старая таблица после миграции
уже не актуальна. Восстановление данных выполняется текущим инструментом с проверкой
итогов; ошибка нового кода исправляется совместимым выпуском без сброса базы.
