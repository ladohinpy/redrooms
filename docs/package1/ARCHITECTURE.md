## Основа
Источник — предоставленный ZIP main, не заново скачанный/угаданный репозиторий.
Исходный commit: 99897cfa7a69b42b944e0ef14caedac983d95052.

уточнения пользователя имеют приоритет. Отсрочены изображения/сторис/реферальные метки.

## Сущности
Текущие каталоги/релизы остаются прежним административным состоянием, доступным через
тот же API. Новая rr_records хранит их отдельной записью `admin` и остальные сущности:
content, contest, player, attempt, reservation, request, moderation, final, finalNote,
visit, template. Нет одной огромной записи со всеми прохождениями.

Поля rr_records: row_id (PK), generation, entity_key, kind, revision, payload JSON.
`commit` — отметка законченной ревизии. `SELECT` фиксирует generation + revision.
Каждая мутация вставляет изменённые записи + commit **одним** INSERT ... SELECT,
условие которого сравнивает последнюю глобальную ревизию. Конфликт вызывает чтение
новой версии и повтор чистой операции; внешние sendDocument не находятся внутри
повторяемой транзакционной функции. Внешний HTTP не считается частью SQL-атомарности.

Не использован выдуманный `db.transaction`: официальный SDK документирует raw db.run
с именованными параметрами и db.get/all с sql-tag. `sdk-bind.mjs` передаёт значения
через tag bindings, а не склеивает пользовательские строки в SQL. Многотабличных
BEGIN/COMMIT через отдельные асинхронные вызовы нет.

Восстановление готовит невидимое поколение на revision0, повторно сверяет логические
данные, затем CAS вставляет актуальную запись admin с положительной ревизией и commit.
Старые открытые редакторы не могут перезаписать восстановленное состояние.
Активная база не меняется при незагруженной части, плохом checksum, новой записи,
ошибке доставки страховочной копии или отсутствии нужной игровой сборки.

Служебные transfer/probe строки не попадают в backup. Исторические физические версии
и завершённые transfer-поколения пока не уплотняются; их очистка не должна появиться
без отдельного тестирования согласованных читателей и копий. Это документированный
предел первой версии, не обещание неограниченной ёмкости.

## Модули
- `record-store.mjs`: versioned CAS, согласованное чтение, staging/restore, старый catalog API.
- `contest-domain.mjs`: подсчёт, признаки аномалий, лучшие попытки, равные места, статистика.
- `contest-service.mjs`: подписанный пользователь, старт/финиш, сроки, контент, модерация,
  неизменяемые итоги, наблюдаемые запуски, предпросмотр без записи попытки.
- `content.mjs`, `rich-text.mjs`: поля и безопасное форматирование; закрытая статья остаётся серверной.
- `backup.mjs`, `backup-service.mjs`: формат, SHA-256, связи, chunks, отправка, предварительная
  проверка и атомарное переключение после страховочной копии.
- `sdk-bind.mjs`, `sdk-probe.mjs`: фактический documented raw SQL contract и облачный smoke.
- `package1-runtime.js`: SDK adapter, проверка назначения, соединение со старым каталогом.
- endpoints `rrContest`, `rrBackup`, `rrDeployment`: разрешённые команды/права.
- `admin-contest.mjs`: вкладки внутри существующей админки; нет второго редакторского каталога.
- `contest-client.mjs`: локальный outbox, старт, размещения, повтор финиша, тексты/ссылка/рейтинг.
- `rr-game-v09.html`: минимальные точки подключения к настоящему игровому коду v08.

## Согласованные правила
100/-75, серверное время финиша, 2 слота, отсутствует автоматический возврат потерянной
попытки. Новая конкурсная попытка не импортирует старый локальный practice-прогресс.
Глобальная модерация не меняет final-снимок: даже имя игрока в нём остаётся прежним.
Пост итогов генерируется из final, не из пересчитанного leaderboard.
Исходные ответы/calculated неизменны, административный adjustment хранится отдельно.

## Миграция
Корневой schema.js получает direct declaration rr_records + индексы, без импорта
из вспомогательного schema-модуля. Сначала add-only migration и probe в облаке,
затем новый backend. При первом обращении он копирует старое состояние один раз.
legacyRevision фиксируется и проверяется: старый backend после перехода не должен
редактировать rr_admin_state. На первой миграции закройте редакторы и не запускайте
конкурс; параллельный ручной деплой блокировать организационно и concurrency group.

## Что здесь не гарантируется
Нативный Telegram не имитируется полностью. Данные клиентов можно подделать,
поэтому телеметрия не является доказательством честности. Полная синхронизация
ходов между устройствами отсутствует. Бот не умеет начинать личный диалог с
администратором без разрешённого контакта. Плановый GitHub job может задержаться.
JSON checksum выявляет повреждение, но не является цифровой подписью автора.
