# Резервные копии: что именно сохраняется

Полный логический JSON формата `redrooms-backup`, version1. Поля createdAt (UTC),
source (environment, botId, revision), records и SHA-256 checksum канонического
содержимого. Это данные приложения, не физическая SQLite и не архив исходников.
Для восстановления нужны этот JSON и совместимая кодовая сборка с прежними games.

Включены административные наборы/релизы/настройки, тексты, конкурсы, игроки,
попытки с ответами/действиями, резервации, ключи идемпотентности, модерация,
официальные итоги и отдельные поздние примечания, наблюдения запусков.
Исключены секреты, разрешённые ID из конфигурации, служебные SQL-ревизии/передачи.

Получатели не задаются клиентом: сервер отправляет один и тот же JSON только двум
ADMIN_IDS. Каждый должен открыть чат с ботом. При отправке из UI виден результат
для каждого получателя; перед деплоем и restore отсутствие хотя бы одной доставки
останавливает процедуру. Повтор после таймаута может прислать повторную копию, но
не меняет данные игры. Документ можно скачать: защита от скачивания не включена.

Транспорт — `InputFile(Uint8Array, name.json, application/json)` из sdk и
`api.sendDocument`; реальная доставка проверяется на stage. Никаких публичных URL
с токенами, ZIP-вложений или загрузки бэкапа в public/ нет.

## Размер

Смотрите BACKUP-SIZES.json, воспроизводится `node scripts/rr-backup-size-example.mjs`.
Это точные байты **модельных** записей выбранного сценария, не замер вашей живой базы.
Исходные 201 кассета и реестр сборок — около 46.4 КиБ. Две завершённые попытки каждого
из 100 игроков на 20 кассет — около 0.59 МиБ, 1000 — 5.84 МиБ. На 201 кассету:
100 игроков — 3.83 МиБ, 1000 — 37.85 МиБ. Дополнительные недели/ошибки/модерация
увеличивают файл; цифры не являются нагрузочным тестом облака.

Защитный предел этой реализации — 40 МиБ на полный файл, ниже 50 MB, документированных
для отправки документа Bot API. Превышение не удаляет/не урезает историю; выдаётся
ошибка и требуется расширение формата порционными файлами. Размеры можно смотреть
до отправки по экспорту. Для небольшой первой группы это не требует компрессии.

## Проверка и восстановление

Файл загружается приватными кусками, затем сервер проверяет checksum, версию,
ссылки набор→сборка, конкурс→каталог, попытка→игрок, лимиты/резервации, финалы.
Наличие нужного game codeHash обязательно; база не заменяет файлы игры.
Старые выгрузки прежней админки поддержаны. При отсутствии в них достоверной даты
отображается «—», а не выдуманная дата. Неизвестный формат отклоняется.

Предпросмотр показывает состав, источник, размер и точную строку подтверждения.
Копия другого бота требует отдельного разрешения. После подтверждения:
1. Свежая страховочная копия двум администраторам.
2. Запись в скрытое поколение и контроль прочитанного результата.
3. Единственная CAS-операция переключения, только если рабочая ревизия не изменилась.
4. Отдельная запись аудита восстановления и новая ревизия редакторского состояния.

Любой конфликт — база остаётся прежней, следует повторить проверку свежих данных.
Во время восстановления разумно закрыть конкурсное окно/редакторские записи, иначе
поступающие финиши безопасно будут отменять переключение. Маскировать конфликт нельзя.
Восстановление старого бэкапа после выпуска новых официальных итогов запрещено,
если оно удаляет или меняет эти итоги. Это намеренная защита договорённости с Виталием.

Проверять восстановление на stage. GitHub fetch сохраняет **код**, не пользовательские
данные. Не считать его заменой JSON-копии. Не хранить JSON игроков в публичном репозитории.
