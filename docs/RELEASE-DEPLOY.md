# Релиз: разово загрузить на прежний сервер с прежним ключом

> Обновление 21.10.2026: [CLI false / локальный снимок и миграция BotFather](FIX-CLI-SNAPSHOT.md).
> Ручное подтверждение в BotFather не требуется перед `migrate --safe`.
> `run endpoints/rrHealth` проверяет локальные исходники в облачной среде; опубликованный Mini App проверяется отдельно.

## Что остаётся прежним

Используем существующий бот и существующий Telegram Serverless-проект.
Для текущего проекта опубликованный адрес — `https://app8804859840.tgcloud.ai/`.
Не создавайте новый бот/проект и не меняйте URL Main Mini App: после успешного обновления
по старому адресу будет новый загрузчик.

Нужен **Serverless CLI Access token** из `BotFather → ваш бот → Serverless → CLI Access`.
Он имеет вид `app<id>:<secret>` и отличается от Bot API token вида `123456:...`.
Ключ не вставляют в HTML, JS, README, CSV, параметры ссылок или сообщения чата.

Если в GitHub уже есть secret `TGCLOUD_TOKEN`, используйте его. Повторно получать или перевыпускать
ключ только ради новой ветки не требуется, если прежний ключ действителен и относится к тому же боту.
При отзыве/истечении ключа CLI завершится ошибкой — тогда актуальный ключ получают в BotFather.

## 1. Подготовить новую ветку

Работайте в актуальном checkout `ladohinpy/redrooms`, а не в пустой распакованной папке обновления.
Проверьте `git status`; сохраните свои незакоммиченные изменения до продолжения.

```bash
git switch main
git pull --ff-only
git switch -c feature/admin-releases
```

Скопируйте **содержимое** папки из ZIP в корень checkout с объединением папок.
Обязательно перенесите `.github/workflows`; остальные файлы существующего репозитория не удаляйте.
`public/index.html` из рабочей версии нужен сборщику: не заменяйте его вручную.

```bash
node scripts/rr-prepare.cjs
node scripts/rr-check.cjs
git diff --stat
```

Если сборщик не нашёл ожидаемую структуру v06 — остановитесь. Корневой HTML ещё не заменён;
нужно адаптировать точки интеграции под настоящий исходник, а не отключать проверки.
Если пройдены проверки, сохраните результат, включая `src/rr-legacy-v06.html`,
`config/rr-built-games.json`, `public/games/`, `public/rr/runtime/` и `public/rr/frozen/`:

```bash
git add .
git diff --cached --stat
git commit -m "feat: admin catalogs and versioned game releases"
git push -u origin feature/admin-releases
```

Это создаёт ветку в вашем GitHub; предоставленный ZIP сам ветку на GitHub не создаёт.
Не используйте `git push --force`. Произвольный push в feature-ветку не публикует production.

## 2. Вписать Павла и Виталия

Нужны **два числовых Telegram user ID**, а не `@username` и не ID бота.
Реальные ID в пакет не включены, потому что они не были предоставлены.
Для разработчика существующего Mini App числовой ID можно посмотреть при реальном запуске
в `Telegram.WebApp.initDataUnsafe.user.id`, но это только подсказка для настройки:
серверное предоставление прав всегда основано на проверенном `ctx.initData`.

Для GitHub Actions создайте **Repository variable** `RR_ADMIN_IDS` в
`Settings → Secrets and variables → Actions → Variables`:

```text
ID_ПАВЛА,ID_ВИТАЛИЯ
```

Замените оба обозначения реальными цифрами без кавычек. Это не секретный ключ.
Production-сборка не пропустит обозначения, пустой список, отрицательные/дробные числа,
один ID, три ID или два одинаковых ID.

Для локального деплоя скопируйте `config/rr-admins.example.json` в
`config/rr-admins.local.json` и заполните `adminIds` массивом двух **чисел**, либо задайте
`RR_ADMIN_IDS` в окружении. Локальный файл и генерируемый server-only allowlist исключены из Git.

## 3А. Разовая публикация через прежний GitHub Actions

Рекомендуемый порядок: PR `feature/admin-releases → main`, просмотр изменений, merge,
затем запуск существующего workflow-файла `publish.yml`, обновлённого этим пакетом.
После merge интерфейс GitHub покажет новые поля workflow. Не ожидайте появления новой формы
ручного запуска до того, как её описание появится в основной ветке.

В `Actions` выберите **Publish Red Room — Admin & Releases** → **Run workflow**:
выберите `main`, в `confirm` введите **PUBLISH**. Поле `admin_ids` можно оставить пустым,
если заполнена Repository variable `RR_ADMIN_IDS`.

Уже сохранённый secret **TGCLOUD_TOKEN используется автоматически**.
В форму workflow секретный token не вставляют.

Workflow устанавливает зафиксированный `@tgcloud/cli@0.2.0` и выполняет:

```text
production-сборка и локальные тесты
    ↓
fetch — обновить локальную ссылку на облачное состояние, не переписать исходники
    ↓
push — новая схема + новые серверные модули + существующая проверка подписки
    ↓
migrate --dry-run — показать изменения БД
    ↓
migrate --safe — применить только безопасные добавления
    ↓
run endpoints/rrHealth — проверка доступа и SQLite на настоящей платформе
    ↓
push public/ — опубликовать загрузчик, админку и все сохранённые игровые сборки
```

Первый запуск создаёт таблицу `rr_admin_state`. Данные и исходный релиз инициализируются один раз.
Повторный запуск не сбрасывает каталоги/релизы. Во время деплоя не редактируйте данные вдвоём:
публикация backend, миграция и frontend — отдельные этапы, не одна общая транзакция.

Если любой этап завершается ошибкой, следующие не выполняются. В частности, при ошибке
первичной миграции/облачного smoke-теста новый frontend не публикуется. Не пытайтесь продолжить
ручным `push public/`, пока причина не устранена.

**Не запускайте после этого старую инструкцию, которая отправляет только исходные три файла.**
Новому загрузчику нужны endpoints `rr*`, схема, библиотека `tgcloud/lib/rr` и все файлы `public`.

## 3Б. Разово с компьютера / Codespaces, в том числе прямо из feature-ветки

Этот вариант не требует предварительного merge: он публикует файлы текущего checkout
в **тот же production-бот**. Само название Git-ветки не создаёт тестовый сервер.

Проверьте два ID из шага 2, затем:

```bash
npm install --save-dev --save-exact @tgcloud/cli@0.2.0
npx tgcloud login
```

На запрос CLI вставьте **прежний Serverless CLI Access token** этого бота.
`login` сохраняет ключ локально для проекта; вводить его при каждом последующем обновлении не нужно.
Каталог `.tgcloud/` управляется CLI: не открывайте и не редактируйте его вручную и не коммитьте его.
Если `TGCLOUD_TOKEN` уже задан в окружении, CLI использует его; проверьте, что он относится
к нужному приложению, а не к другому тестовому боту.

Публикация с явным подтверждением:

```bash
node scripts/rr-deploy.cjs --confirm
```

Без `--confirm` скрипт ничего не публикует. `rr-prepare` и `rr-check` сами по себе не вызывают сеть.
CLI зафиксирован на 0.2.0: при установке другой версии сначала сверьте обновлённую документацию
и адаптируйте контракт, а не подменяйте версию без проверки.

`rrHealth` вызывается через привилегированный CLI с синтетическим контекстом одного настроенного
администратора. Это проверка разработчика; публичное API не принимает такой контекст из входного JSON.
Она проверяет чтение/первичную запись SQLite, но не заменяет реальный запуск с подпиской и Telegram initData.

При конфликте с облаком публикация останавливается. Сначала выясните, кто менял сервер.
`fetch` безопасен для ваших файлов; **`pull` может перезаписать локальные изменения**.
Не используйте `--force`, `reset` или удаление таблиц как универсальное «исправление».

## 4. Проверка после публикации — обязательна

Откройте игру внутри настоящего Telegram, не просто URL в Safari/Chrome.

- Подписчик попадает в исходный `classic-1`, если default ещё не меняли. Неподписчик видит предложение
  подписаться; сетевой сбой не должен давать доступ. Канал остаётся из существующего `checkAccess.js`.
- Павел и Виталий видят «Админка». Посторонний аккаунт не получает доступ даже по `startapp=admin`.
- Создайте копию каталога, измените один фильм, сохраните, опубликуйте, создайте тестовый релиз.
  До публикации он открывается вам и недоступен обычному подписчику.
- Опубликуйте релиз. Проверьте специальную ссылку; сделайте основным и проверьте новый обычный запуск.
  Ранее открытая партия не должна поменяться. Ссылка `release=classic-1` должна продолжать работать.
- Проверьте второй телефон, Android/iOS: управление v06, загрузка файлов, прокрутка админки,
  сохранение прогресса после закрытия Mini App, доступность старой партии по её ссылке.

Если возникло несовпадение SDK, структуры реальной v06 или поведения Telegram WebView,
не считайте это закрытым по одному зелёному локальному тесту. Исправьте и повторите ручную проверку.

## 5. Откат и дальнейшая работа

**Неудачная коллекция:** в админке выберите предыдущий опубликованный релиз и нажмите
«Сделать основным». Деплой и новый ключ для этого не нужны.

**Ошибка нового кода:** верните предыдущую проверенную сборку с новым/старым разрешённым релизом.
Не удаляйте старые `public/games`, `public/rr/runtime` и `public/rr/frozen`: на них могут вести ссылки.
Если сама новая оболочка не работает, возврат известной рабочей папки `public` возможен отдельной
публикацией статики из сохранённого checkout. Не откатывайте/не очищайте таблицу вместе с HTML.
Перед ручными действиями сохраните текущую ветку и backup данных.

Смена фильмов, модерация, новый каталог для уже загруженного кода, выбор default — только админка.
Новая механика или исправление кода — Git, новый ID сборки, проверки и повторный явный деплой.
Существующий CLI token может использоваться снова, пока он действителен.
