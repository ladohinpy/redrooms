# Универсальный бот проверки подписки — механизм до реализации

Это согласуемая архитектура, а не работающий бот. По просьбе владельца бот пока
не создаётся. У нас ещё нет @имени, токена и списка каналов. Игра v06 работает
самостоятельно и НЕ ограничивает доступ подпиской.

## 1. Что получает игрок

Игрок открывает бота или ссылку Mini App, нажимает «Играть». Если подписка нужна,
видит короткий экран: «Подпишитесь на канал, чтобы войти», кнопки каналов и
«Проверить подписку». После подписки возвращается в игру; проверка запускается
повторно. При успешной проверке сразу появляется вход в комнату. После возврата
из канала можно автоматически перепроверить статус, но оставить кнопку для
случая, когда Telegram ещё не обновил данные.

Если Telegram/API недоступен: «Не удалось проверить. Попробуйте ещё раз».
Ошибка связи — не утверждение, что человек не подписан, и не разрешение доступа.

## 2. Что нужно технически

Один бот и небольшой сервер с HTTPS. Игру можно оставить одним HTML и сохранить
адрес https://zindone.ru/redrooms2. Сервер проверок работает отдельно от графики.
Предпочтительно отдать API на том же домене, например под /api/redroom/ — это
предлагаемый путь, сейчас такого API у проекта нет.

Схема одного входа:

```text
Игрок → Mini App бота → сырой Telegram initData → ваш HTTPS-сервер
                                                  ↓
                                    проверка подписи и срока данных
                                                  ↓
                              конфигурация кампании и её каналов
                                                  ↓
                               Telegram Bot API: getChatMember
                                                  ↓
                        подписан → короткая сессия → доступ к игре
                        нет      → ссылки каналов → перепроверка
                        ошибка   → повторить позже, доступ не выдавать
```

Клиент не отправляет «мне можно» и не выбирает произвольный Telegram user_id.
ID игрока сервер извлекает только из подписанных Telegram данных.
Нельзя доверять `initDataUnsafe`, данным query string или localStorage как
доказательству личности. [Проверка данных Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

## 3. Что бот может узнать о подписчиках

Bot API позволяет проверить КОНКРЕТНОГО пользователя через `getChatMember`.
Надёжная проверка других пользователей гарантируется, когда бот — администратор
проверяемого канала. Это не выгрузка всего списка подписчиков. Число подписчиков
через `getChatMemberCount` также не даёт их список.
[getChatMember](https://core.telegram.org/bots/api#getchatmember),
[getChatMemberCount](https://core.telegram.org/bots/api#getchatmembercount).

Сопоставление результата:

| Статус Telegram | Доступ по этому каналу |
|---|---|
| creator / administrator / member | Подписка подтверждена |
| restricted | Только если is_member = true |
| left / kicked | Подписка не подтверждена |
| неизвестный статус, timeout, 403, 429, бот не администратор | Проверка недоступна; не выдавать сессию |

Если бот удалён из канала, уведомляем владельца. Нельзя скрытно пропускать такой
канал и допускать всех. В режиме `any` положительный результат хотя бы одного
канала достаточен; если положительных нет, но есть ошибка, показываем недоступность,
а не окончательный отказ. В режиме `all` нужны подтверждения всех активных каналов.

## 4. Каналы меняются без правки кода

Бот должен обслуживать несколько кампаний: `redroom`, следующая игра, розыгрыш
и т. п. У каждой — название, список каналов и правило `all` (все) / `any` (любой).
Пример формата лежит в channels.example.json. Это проект контракта, сейчас файл
не читается игрой и не включает проверку сам по себе.

Предлагаемое меню владельца в личном диалоге с ботом:

- «Кампании» → выбрать или создать кампанию.
- «Каналы» → добавить @username или числовой chat_id закрытого канала.
- Бот сам проверяет существование канала и свои права; владелец задаёт название
  кнопки и ссылку вступления. Для закрытого канала ссылка приглашения хранится
  отдельно от числового ID; join-request не считается членством до одобрения.
- «Условие доступа» → все каналы / любой канал.
- «Предпросмотр» → показать будущий экран игрока, список изменений и подтвердить.
- «Экспорт/импорт JSON» → перенос настроек между играми. Импорт валидируется
  целиком, старая конфигурация сохраняется до успешного подтверждения.

Равнозначные будущие команды: `/campaigns`, `/channels`, `/addchannel`,
`/removechannel`, `/policy`, `/export`, `/import`. Это предложенный интерфейс,
а не команды уже существующего бота. Административные действия доступны только
числовым Telegram ID из серверного `ADMIN_IDS`, не по изменяемому @username.
Настройки хранятся в БД или постоянном томе сервера, переживают перезапуск.

Включённая кампания с пустым списком — ошибка конфигурации, а не «разрешить всех».
Публичный режим, если нужен, должен быть отдельным явным решением владельца.
Изменение каналов увеличивает configVersion и аннулирует старый кэш доступа.

## 5. Безопасность проверки и сессий

На сервере токен задаётся секретом окружения `TELEGRAM_BOT_TOKEN`.
Фронтенд передаёт raw initData по POST HTTPS. Сервер по официальному алгоритму
проверяет HMAC-SHA-256 в постоянном времени и обязательный `auth_date`.
Для HMAC secret_key = HMAC_SHA256(key="WebAppData", message=bot_token), затем
HMAC_SHA256(secret_key, data_check_string). Поля сортируются, `hash` исключается;
не смешивать этот алгоритм с отдельной Ed25519-проверкой для третьих сторон.
Не декодировать вход повторно, отклонять дубли полей и повреждённый JSON.
[Официальный алгоритм](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app).

Рекомендуемая политика приложения (настраиваемая, не ограничение Telegram):
принимать свежий initData, например до 10 минут с допуском часов 30 секунд;
после успешного обмена выдавать короткую серверную сессию. Долгая партия должна
продлевать уже подтверждённую сессию, а не постоянно обменивать устаревший initData.
При истечении сессии предложить заново открыть Mini App. initData — bearer-данные:
не записывать в аналитику/логи/URL, защищать от XSS и повторного злоупотребления.

Кэш проверки: 60–120 секунд на user + campaign + configVersion, ограниченный
по размеру; ошибки API не кешируются как «подписан». Ограничение частоты запросов
на сервере, timeout, обработка Telegram retry_after. Проверять снова перед
серверной наградой/важным действием, а не при каждом взятии кассеты.

Сессия — случайный серверный идентификатор в Secure/HttpOnly cookie с разумным
SameSite, TTL и серверным хранением, либо иной явно спроектированный механизм.
Для разных доменов нужно отдельно решить CORS/cookies; проще same-origin API.
Нельзя выставлять доверенные CORS на «*» с credential-запросами.
Webhook защищается секретным заголовком, админ-операции — авторизацией и CSRF-защитой.

Статический HTML всегда можно скачать и изменить. Если защита касается доступа
к самому файлу — сервер должен проверять сессию при его выдаче. Если защита
касается призов/рейтинга — только сервер выдаёт их и валидирует результат.
Простое скрытие кнопки «Играть» и клиентские очки не защищают призовой конкурс.
Эта версия не содержит серверного античита или проверенных рейтингов.

## 6. Что значит «отслеживать»

Первая версия сервиса проверяет текущего вошедшего игрока по запросу. Для
повторного контроля можно добавить `chat_member` updates в allowed_updates
webhook и сбрасывать кэш знакомых пользователей при выходе из канала.
Это не восстанавливает исторический список всех подписчиков и не заменяет
проверку на входе после пропущенных событий.
[Updates Bot API](https://core.telegram.org/bots/api#update).

Хранить достаточно user_id, campaign_id, результат и время последней проверки,
версию настроек, срок сессии. Не сохранять лишние профили, не выгружать чужую
аудиторию и не отправлять рекламу автоматически. Сроки хранения и текст
политики конфиденциальности определяются перед запуском.

## 7. Правильная ссылка и полноэкранный запуск

Обычная ссылка `https://zindone.ru/redrooms2` не становится Mini App от того,
что её открыли в Telegram. В BotFather владелец настраивает Main Mini App на
этот HTTPS-адрес и/или кнопку меню, а в боте — кнопку типа `web_app`.
Для этого сценария подходит `InlineKeyboardButton.web_app` под сообщением,
кнопка меню или Main Mini App. Обычная reply-клавиатура с `sendData` — другой
путь интеграции, не замена подписанному серверному входу. При отсутствии валидного
initData защищённая версия предлагает открыть Mini App, а не пропускает проверку.

Шаблон для настроенного Main Mini App:
`https://t.me/BOT_USERNAME?startapp=redroom&mode=fullscreen`

Для именованного Mini App:
`https://t.me/BOT_USERNAME/APP_SHORT_NAME?startapp=redroom&mode=fullscreen`

Это ШАБЛОНЫ, не действующие ссылки. Кампания определяется по проверенному
`start_param` в initData; внешний параметр используется максимум как подсказка UI.
Сервер принимает только известные включённые кампании.
[Официальные ссылки Mini Apps](https://core.telegram.org/api/links#mini-app-links).

Внутри Telegram игра запрашивает fullscreen (API 8.0+) и отключает вертикальное
сворачивание (7.7+). Это не отключает все системные жесты и не гарантирует
полный экран на старом клиенте. Вертикальная шапка остаётся способом выхода.
[Mini Apps API](https://core.telegram.org/bots/webapps).

## 8. Порядок реализации после согласования

1. Владелец создаёт бота в BotFather, задаёт @имя и передаёт токен непосредственно
   в секреты сервера — не в HTML, репозиторий или публичный чат.
2. Выбирает каналы и добавляет бота администратором с минимальными нужными правами.
3. Разработчик разворачивает API, постоянное хранилище и меню администратора;
   проверяет getMe и права бота в каждом канале.
4. Подключает в игру экран доступа и сессии. Настраивает Mini App, web_app-кнопку,
   HTTPS, webhook secret и подтверждённую ссылку распространения.
5. Проверка двумя реальными аккаунтами: подписан / не подписан; затем выход из
   канала, ошибка API, снятые права бота, закрытый канал и режимы all/any.
6. Реальные iPhone/Android: прямой Mini App, кнопка бота, обычная HTTPS-ссылка,
   поворот, системный Back, возвращение из канала. Только после этого публикация.

Для следующего шага нужны: согласие на эту схему, список каналов, правило all/any
и возможность разместить небольшой backend рядом с существующим сайтом.
