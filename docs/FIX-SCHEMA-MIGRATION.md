# Исправление остановки на `tgcloud migrate --dry-run`

## Что произошло в присланном журнале

Подготовка игры завершилась (201 фильм, 4 режиссёра, 2 ID администраторов).
Все 100 исходных локальных тестов прошли. `tgcloud fetch` завершился успешно.
Загрузка 13 новых серверных модулей также завершилась (`Done in 2.1s`).
Затем процесс остановился на:

```text
> tgcloud migrate --dry-run
Error: Module error: Invalid module: Cannot find module by name: 'lib/rr/schema'
```

Это не повтор предыдущей ошибки синхронизации и не ошибка выбора Action.
В этом запуске серверный код уже отправлен; команды применения миграции,
облачной проверки `rrHealth` и публикации `public/` ещё не выполнялись.
Успех загрузки модулей не подтверждает успешность их выполнения.

## Что меняет патч

В исходном пакете `scripts/rr-prepare.cjs` дописывал в `tgcloud/schema.js`:

```js
export { rrAdminState } from './lib/rr/schema.js';
```

В присланном запуске мигратор не смог загрузить эту зависимость. По одному
журналу нельзя установить внутреннюю причину поведения облачного загрузчика.
Патч исключает саму зависимость из точки входа миграции:

- объявление `rr_admin_state` находится непосредственно в `tgcloud/schema.js`;
- из корневой схемы для этой таблицы импортируется только `sdk/db`;
- старый путь `tgcloud/lib/rr/schema.js` остаётся совместимым экспортом ИЗ
  корневой схемы, чтобы не менять вызывающий `store.js`;
- сборщик автоматически удаляет точный старый сгенерированный экспорт,
  сохраняет остальные объявления и не возвращает проблемную ссылку;
- повторная сборка даёт тот же результат;
- при нестандартном определении `rrAdminState`, повреждённых маркерах или
  ручном изменении управляемого блока сборка останавливается вместо перезаписи.

Имена таблицы и полей, типы и ограничения НЕ меняются:
`rr_admin_state(id TEXT PRIMARY KEY, revision INTEGER NOT NULL, state_json JSON NOT NULL)`.
Это описание DSL, не новая SQL-команда для ручного выполнения.
Патч не выполняет SQL и ничего не публикует автоматически.


Архив содержит пути от корня проекта.
`tgcloud/schema.js` намеренно НЕ вложен: его корректно обновляет сборщик,
не заменяя чужие таблицы универсальной копией файла.

## Как применить через GitHub

1. В актуальном репозитории `ladohinpy/redrooms` создай ветку исправления
   от текущего `main`, например `fix/schema-migration`.
2. Распакуй архив и перенеси его содержимое в корень репозитория с сохранением
   путей. Не удаляй остальные файлы проекта. Не помещай папки внутрь
   дополнительной папки `redrooms-schema-migration-fix`.
3. Создай коммит, проверь PR и объедини его с `main`.
4. Открой **Actions → Publish Red Room — Admin & Releases → Run workflow**.
   Выбери `main`, введи `PUBLISH`; используй те же ID администраторов или
   ранее настроенную `RR_ADMIN_IDS`. Секрет `TGCLOUD_TOKEN` оставь прежним.
5. Создай НОВЫЙ запуск на коммите с исправлением. Не запускай заново старый
   упавший запуск: для проверки нужен исправленный код.

Workflow `.github/workflows/publish.yml` и скрипт `scripts/rr-deploy.cjs`
этим патчем не меняются. В предыдущем запуске они уже довели процесс до
нужной команды миграции.

## Локальные команды (альтернатива работе только в интерфейсе GitHub)

После копирования файлов, из корня существующего проекта:

```bash
node scripts/rr-prepare.cjs
node scripts/rr-check.cjs
```

Для запуска только тестов без подготовки настоящей игры:

```bash
node scripts/rr-check.cjs --tests-only
```

Нужен Node.js 22, как в текущем workflow. Производственная публикация — только
через существующий ручной workflow либо осознанно через:

```bash
node scripts/rr-deploy.cjs --confirm
```

## Что проверено

На Node.js 22.16.0 выполнено 113 тестов: 113 успешно, 0 ошибок.
Это 100 исходных тестов и 13 новых проверок схемы. Новые проверки включают:
обновление прежнего экспорта, отсутствие зависимости корневой схемы от
`lib/rr/schema`, сохранение посторонних таблиц, отсутствие повторных вставок,
защиту от повреждённых и изменённых объявлений, повторную настоящую сборку
тестового проекта и локальное выполнение схемы с подставленным `sdk/db`.

Локальная проверка с подставленным SDK НЕ равнозначна запуску в Telegram.
В облаке патч из этой среды не публиковался, `migrate` и `rrHealth` здесь не
выполнялись. Секрет не запрашивался и не использовался.

## Что должно произойти при следующей публикации

Порядок прежний: подготовка → тесты → fetch → загрузка серверных модулей →
`migrate --dry-run` → `migrate --safe` → `rrHealth` → загрузка `public/`.

Устраняем конкретный импорт, на котором остановился предыдущий запуск.
Окончательное подтверждение даёт новый облачный запуск. Если возникнет другая
ошибка, не обходи её через `--force`, не удаляй базу и не отключай `rrHealth`.
Ищи первую строку `Error` после последней строки `> tgcloud ...`.
