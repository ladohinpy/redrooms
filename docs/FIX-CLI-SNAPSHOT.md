# Исправление остановки CLI после push (21.10.2026)

## Что установлено по присланному main, журналу и скриншоту

Исходная точка: архив `redrooms-main (1)(1).zip`, предоставленный владельцем.
В нём уже есть исправленный `rr-prepare.cjs`: он размещает объявление таблицы
непосредственно в `tgcloud/schema.js`. Файл `tgcloud/lib/rr/schema.js` — намеренный
совместимый экспорт, нужный `store.js`; не удаляйте его как «старый».
Пустая корневая схема в исходном ZIP не означает, что патч потерян: prepare добавляет
управляемый блок перед push. Оригинальный игровой HTML также преобразуется prepare.

Последний журнал: 113 тестов прошли; fetch получил 15 модулей, revision 2; push
сообщил о загрузке двух схем. Затем `replaceSnapshot → writeSnapshotFile → fs.writeFileSync`
получил `false` вместо текста. До migrate и финальной статики выполнение не дошло.
Токен и права не являются причиной именно этого TypeError. Код мог уже примениться
на сервере, хотя процесс завершился с кодом 1.

По коду опубликованного CLI 0.2.0, после успешного batchDeploy в replaceSnapshot
передаётся response.canonical_modules без проверки типа значений.
Причина появления false в ответе сервера НЕ установлена: сырой ответ в журнале
отсутствует. Исправление не предполагает, что false означает удаление или отсутствие изменений.

## BotFather и миграция — не конфликт

Документация разделяет публикацию кода и изменение базы:

1. push загружает JavaScript, включая описание схемы; таблицы от этого не создаются.
2. migrate сравнивает опубликованную схему с фактической базой и применяет изменения.
3. migrate --dry-run ничего не применяет.
4. migrate --safe применяет только safe-изменения без интерактивного вопроса,
   пропускает warning/manual. Код возврата 0 сам по себе не гарантирует, что
   пропущенных изменений нет, поэтому после него оставлен проверочный rrHealth.

Экран `Database → Migration → + rr_admin_state (add table)` показывает ожидающее
создание таблицы. Это не блокировка Actions до ручного подтверждения. Можно сделать
то же изменение вручную в BotFather, но это не исправит ошибку записи локального снимка CLI.
Предпочтительный путь здесь: оставить миграцию workflow, не нажимать одновременно
Start Migration и не редактировать облачный код во время публикации.

Если таблица уже создана вручную, не удаляйте её. При соответствии схеме CLI сообщит,
что изменений нет. Во всех случаях проверьте результат dry-run; неожиданные изменения
таблиц требуют отдельного разбора.

## Что делает этот патч

Добавляет узкий локальный адаптер совместимости для **@tgcloud/cli 0.2.0**.
Это исправление проекта, не официальный новый выпуск CLI.

`scripts/rr-cli-compat.cjs` меняет один точно опознанный блок в установленном
`node_modules/@tgcloud/cli/src/commands/deploy.js` перед запуском CLI. В Git попадёт
скрипт патча, а не node_modules. При другой версии или иной структуре блока публикация
останавливается до сетевых операций. Повторное применение идемпотентно.

`scripts/rr-cli-response.mjs` обрабатывает только наблюдавшийся случай: в
canonical_modules встречается boolean false. Он делает один дополнительный **read-only**
GET /get через существующие функции и авторизацию CLI, то есть получает полный снимок.
Перед его использованием обязательны:

- та же числовая server revision, что в успешном ответе push;
- текстовое содержимое каждого модуля;
- полный набор имён, совпадающий с manifest отправки кода;
- сохранение исходных полей static, db_changes и revision.

Для публикации только статики manifest кода отсутствует: дополнительно проверяется,
что полный снимок содержит все модули, названные в исходном ответе.

Если чтение не удаётся, ревизия изменилась, набор неполон или снова встречается false,
процесс останавливается. Никаких String(false), подстановки пустого файла, пропуска
ошибки или повторного push. Существующие проверки expected_revision остаются на месте.
Не используются --force, --yes, сброс БД или автоматическое удаление таблиц.
Исправление локального снимка не управляет миграциями и не создаёт таблицы.

## Как применить

Патч предназначен поверх именно присланного main. Новый код игры, каталоги и ID
администраторов не меняются.

1. Создайте ветку `fix/cli-snapshot-response` от текущего main.
2. Распакуйте патч. Перенесите его содержимое в корень репозитория, сохранив пути
   scripts/, tests/, docs/ и .github/. Не добавляйте лишнюю папку с именем архива.
3. Сохраните изменения, откройте PR и перенесите его в main после проверок.
4. Запустите НОВЫЙ Run workflow: `Publish Red Room — Admin & Releases`, ветка main,
   confirm = PUBLISH. Прежний TGCLOUD_TOKEN и RR_ADMIN_IDS остаются прежними.

Workflow проверки PR теперь сначала делает prepare, а затем запускает все tests/rr;
прежний check.yml проверял только старую игру через старое package.json.

Порядок публикации сохраняется:

```text
local CLI compatibility guard
prepare + tests
fetch
push backend
migrate --dry-run
migrate --safe
run endpoints/rrHealth
push public/
```

Команда `run endpoints/rrHealth` запускает локальные исходники в облачной среде с
базой бота (так устроен CLI run). Она проверяет совместимость кода и БД, но не заменяет
отдельную проверку опубликованных endpoints через настоящий Mini App.

В логе ожидается:

```text
CLI 0.2.0 response guard ready. No deployment performed.
```

Только если снова приходит false, появится:

```text
RR CLI 0.2.0: ответ содержит false вместо текста; читаем полный снимок, без повторного push.
```

При отсутствии изменений после ранее частично успешного push CLI может написать
`No changes to deploy` — это нормально. Далее должна выполняться проверка миграции.

## Полный архив и патч

Патч содержит только файлы исправления; применяйте поверх существующего checkout.
Полный архив в той же выдаче собран из присланного main плюс этого патча. В нём есть
оригинальная v06, подготовленная оболочка и закреплённые игровые ресурсы. Резервная
исходная v06 хранится в src/rr-legacy-v06.html. Старые игровые ресурсы не очищаются.
Не используйте одновременно оба архива и не загружайте ZIP целиком как файл исходников.
Секретов и настоящих Telegram ID в архивах нет; allowlist генерируется при публикации.

## Проверки и границы уверенности

К патчу добавлены 38 автоматических локальных тестов: обычные ответы, false,
повреждённые типы, отказ чтения, несовпадение ревизии и manifest, повторная установка,
проверка синтаксиса, воспроизведение writeFileSync(false) и устранение его в модели
обработчика ответа CLI. Это НЕ полный установленный CLI и НЕ живой сервер Telegram.
Все прежние тесты сохранены. Итоговый локальный прогон приложен в CLI-SNAPSHOT-TESTS.txt.
Реальный токен не использовался, BotFather и сервер из этой сессии не изменялись.
Облачный результат нужно подтвердить новым запуском и ручной проверкой Mini App.
