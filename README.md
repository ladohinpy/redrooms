### Обычный рабочий цикл

1. Создать или полностью скопировать набор. Старый набор и его результаты не меняются.
2. Сохранить четыре списка, заполнить материалы. Годы по-прежнему необязательны.
3. Опубликовать по ссылке. Публикация набора **не запускает конкурс автоматически**.
4. Проверить предпросмотр. Администраторы проходят игру вне зачёта.
5. Во вкладке «Конкурс» нажать «Начать конкурс», при необходимости указать окончание.
6. Проверять статистику и спорные попытки. После закрытия окна закончить модерацию.
7. «Опубликовать окончательные итоги»: места и имена фиксируются навсегда.
8. Скопировать итоговый пост. Его публикация в канал остаётся ручной.

Тексты поддерживают абзацы, **жирный**, *курсив*, `[подпись](https://...)`, отдельную
ссылку и её подпись. HTML не исполняется. Внутреннее описание не передаётся игроку.
Для успешного финала задаётся порог точности (по умолчанию 80%).
Статья раскрывается после конца конкурсного окна либо, по явной настройке, после
двух израсходованных и закрытых попыток; можно скрыть её полностью. Закрытый текст
не входит в публичный ответ API. Для администратора предпросмотр доступен полностью.

### Две попытки и расчёт

Одна попытка резервируется сервером **перед началом игры**, а не в момент финиша.
Одновременное открытие на двух устройствах не создаёт две активные попытки.
Лимит не снимается очисткой localStorage. Если локальный прогресс потерян, автоматического
возврата слота нет: игрок может оставить попытку незавершённой, а администратор —
технически аннулировать её с причиной. Запись остаётся в истории.

Формулы не изменены: **+100 за верное размещение, −75 за ошибочное**;
точность — округлённые `100 × верные / все попытки размещения`.
На финише сервер сам проверяет ответы и воспроизводит последовательность размещений.
Переданный клиентом итоговый score/accuracy не принимается. Правильные ответы привязаны
к неизменяемой опубликованной версии набора. В рейтинг идёт лучший из двух результатов;
равные баллы дают одинаковое место (1, 1, 3). Время не является дополнительным критерием места.

Результат и последовательность сохраняются локально до подтверждения сервера.
При повторной отправке возвращается та же попытка. Время приёма сервером, а не часы
игрока, определяет зачёт. Поздний финиш сохраняется вне зачёта. Повтор ранее принятого
финиша после окончания окна остаётся подтверждением прежнего результата.

Несогласованные действия, ответы и очень короткое время отмечаются для проверки.
Нет автоматических банов. Клиентскую последовательность тоже можно подделать;
это контроль аномалий для дружеского конкурса, **не криптографический античит**.
Движение мыши и каждый кадр не отправляются: сетевые записи — старт и финиш.

### Модерация и неизменяемые итоги

Доступны подтверждение, пометка, корректировка зачётного балла с причиной, техническое
аннулирование, глобальное исключение и восстановление игрока. Первоначальные ответы
и расчёт не переписываются, решения хранят автора/время/до/после/объяснение.

**Официальный итог — отдельный неизменяемый снимок.** Позднее исключение пересчитывает
текущие и будущие рейтинги, но не меняет старые места, Telegram-имена, опубликованный
пост или статус прошлого конкурса. Добавляется отдельная административная пометка.
Повторить конкурс можно только на копии набора. Архив доступен для свободной игры,
но его новые результаты не изменяют официальный рейтинг.

### Ссылки и аналитика

Кнопки до игры и на финише копируют или открывают Telegram-шаринг **именно выбранного
выпуска**, например `https://t.me/BOT?startapp=release_SET_ID`. Админская ссылка
`?startapp=set_SET_ID` ведёт к тому же набору. Персональные метки не добавляются.

Сохраняются наблюдавшиеся сервером запуски Mini App по подписанным данным, запуск
с параметром набора и переход «не подписан → подписан», увиденный в игре.
Это **не счётчик репостов, отправленных сообщений, подписок на бота или `/start`**.
Новый bot handler не добавлен. Полная атрибуция и рефералы отложены.

## Резервные копии и данные

Подробности: [BACKUP.md](docs/package1/BACKUP.md).

JSON содержит редакторскую базу, материалы, конкурсы, игроков, попытки, исходные
действия, лимиты, ключи повторных запросов, решения, итоговые снимки и наблюдаемые запуски.
Экспорт читает свежую согласованную версию сервера, а не ранее открытый экран.
Токены и allowlist не входят в копию. Код игры хранится отдельно в Git/архиве выпуска.

Копии отправляются документами в личный чат **каждого из двух настроенных администраторов**.
В caption — название RedRooms, дата UTC, среда, размер и назначение JSON.
Администраторы должны один раз открыть личный чат с ботом и разрешить сообщения.
Игроков это не касается: для игры обязательным `/start` не становится.

Предусмотрены ручная выгрузка, отправка из админки, копия перед каждым деплоем и
GitHub workflow `Red Room — Private JSON Backups` ежедневно в **03:17 UTC**.
Расписание исполняет GitHub, не ChatGPT; запуск зависит от доступности runner/настроек
репозитория и может задержаться. Проверяйте успешность Actions.

Лимит приложения — **40 МиБ на полный JSON**. Большая копия не обрезается: операция
останавливается, а деплой/восстановление не продолжается без страховочной копии.
Это не лимит SQLite и не обещание нагрузочной ёмкости. Для роста за пределы этого
формата потребуются порционные копии/очистка служебной истории, их здесь нет.

Восстановление: загрузить JSON → увидеть состав/среду/контрольную сумму → подтвердить
точной строкой. До изменения обеим администраторам отправляется текущая копия.
Данные загружаются в невидимое поколение, проверяются, затем рабочий указатель
переключается одной условной SQL-операцией. Любая новая запись во время процедуры
отменяет переключение. Чужая среда требует отдельного согласия. Нельзя стереть или
изменить уже существующий официальный итог старой копией.

## Архитектура и миграция

Новая таблица **`rr_records`** хранит отдельные логические записи игроков, попыток,
конкурсов и т. д., а не всё в одном общем JSON. Запись изменённых сущностей и отметки
ревизии выполняется одним SQL statement с условием предыдущей ревизии. Чтение и
backup привязаны к согласованной ревизии. Полная схема описана в [ARCHITECTURE.md](docs/package1/ARCHITECTURE.md).

`rr_admin_state` не удаляется: при первой инициализации её состояние переносится
один раз. Повторный деплой ничего не сбрасывает. После перехода источником истины
становится `rr_records`; старая таблица не синхронизируется обратно. Обнаруженное
изменение старой таблицы после переноса блокирует работу вместо молчаливого затирания.
**Нельзя откатывать backend на старый архив, который читает только rr_admin_state.**

Старые клиентские страницы используют прежние API каталога через адаптер. Новая
комната использует v09; ранее начатый локальный прогресс не объявляется конкурсной
попыткой. Для конкурсных/тестовых попыток сохранения разделены по attempt ID.

## Публикация

[INSTALL.md](docs/package1/INSTALL.md) содержит точные шаги. Сохраняется Action
**Publish Red Room — Admin & Releases** для текущего stage. Добавлен отдельный
**Publish Red Room — PRODUCTION** с другим ключом и проверкой имени бота.

Последовательность: подготовка/тесты → сверка бота → JSON обоим администраторам →
fetch → только добавочная схема → dry-run/safe migration → облачная проверка SQL
на изолированной служебной записи → backend → rrHealth → frontend.
При неудаче этап останавливается; `--force`, `--yes`, DROP и очистки базы не добавлены.
Ключи и два ID остаются в Actions; их в ZIP нет.

Локальные тесты не подтверждают SDK-контракт живого облака. Для него новый деплой
содержит отдельный probe; реальные Android/iOS, подписка, два аккаунта и получение

историю целиком; это первая версия для небольшого сообщества, не готовый сервис

уплотнения нет. Тестовые данные в `tests/` не публикуются в `public/`.

Не входят: изображения результатов, native shareMessage, сторис, QR, персональные
рефералы, автопостинг, внешняя база, полная синхронизация прогресса между устройствами.
